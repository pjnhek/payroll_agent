## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo → CI runner | Registry data and generated markdown are read by a CI step that gates merges |
| test source → guard | The guard parses arbitrary test source with `ast.parse` (no `eval`, no import of the parsed file) |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-01 | Tampering | `tests/assertion_inventory.py` | high | mitigate | Entry `source_text` is re-extracted from live source and compared exactly (`test_every_entry_source_text_matches_live_source`), so an entry edited to hide a real assertion fails CI rather than silently narrowing the guard |
| T-22-02 | Repudiation | conversion ordering | high | mitigate | The `Assertion inventory precedes conversion (GUARD-01 gate)` CI step turns a planning convention into a merge block, so "the inventory came first" is a verifiable fact, not an author claim |
| T-22-03 | Elevation of Privilege | guard's AST parsing | low | accept | `ast.parse` performs no execution and the guard never imports the files it parses; the input is repo-local source already trusted enough to run under pytest |
| T-22-04 | Information Disclosure | `docs/ASSERTION-INVENTORY.md` | low | accept | The view renders test-source excerpts already public in the repo; captured `source_text` must not be widened to include fixture payloads |
</threat_model>
